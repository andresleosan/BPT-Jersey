# T017 MFA TOTP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans (recommended). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Require TOTP MFA for `owner` and `administrator`, with guided first-login enrollment and backend enforcement from Firebase Auth second-factor evidence.

**Architecture:** Firebase Web Auth owns TOTP enrollment, secrets, challenges, and factor state. The web auth boundary exposes typed operations while `AdminAuthProvider` maps first-factor, enrollment, challenge, and authorized states; `AdminGate` never renders `AdminShell` until the second-factor state is valid. Functions validates `request.auth.token.firebase.sign_in_second_factor === "totp"` for sensitive administrative calls.

**Tech Stack:** Firebase Web SDK 12, Firebase Functions v2, Firebase Admin Auth token claims, React 19, Next.js 16 static export, TypeScript strict mode, Vitest/Testing Library, Playwright.

## Global Constraints

- Second factor is TOTP compatible with authenticator applications; SMS/Phone Auth is not added.
- Owner and administrator cannot access the admin shell or sensitive Functions with first factor only.
- Firebase Authentication is the only authority that stores/verifies the TOTP secret.
- TOTP secrets, QR/URI values, verification codes, tokens, cookies, storage state, screenshots, traces, and logs never enter Firestore, RTDB, custom claims, localStorage, Git, or reports.
- `mfaEnrolled` is not accepted as proof of recent MFA; backend authority is `request.auth.token.firebase.sign_in_second_factor === "totp"`.
- Client users do not require MFA in this task.
- No public bypass, fixed test code, SMS factor, data migration, or destructive operation is introduced.
- Real TOTP E2E is opt-in in local/staging only; CI uses mocks/contracts without MFA secrets.
- Recovery requires operator intervention in Firebase Auth to remove/re-enroll the factor.

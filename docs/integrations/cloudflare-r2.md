# Adaptador Cloudflare R2

Members usa un bucket privado de Cloudflare R2 mediante la API S3-compatible. Las Functions son la única capa que conoce las credenciales y emite URLs firmadas de `PUT` para PDFs temporales.

- Dependencias fijadas: `@aws-sdk/client-s3@3.1107.0` y `@aws-sdk/s3-request-presigner@3.1107.0`.
- El adapter valida `application/pdf`, nombre seguro y un máximo de 10 MiB antes de firmar.
- Las URLs duran como máximo 10 minutos y fijan bucket, object key, tipo y tamaño esperados.
- Los object keys quedan bajo `academies/{academyId}/member-imports/{sessionId}/`; nunca se genera una URL pública.
- La sesión durable con sus object keys se persiste antes de solicitar URLs. El adapter de lectura consume `AsyncIterable<Uint8Array>` con límite de 10 MiB durante el stream; los tests inyectan streams, signer y borrado, sin leer `.env`, claves R2 ni acceder a un bucket real.
- Las credenciales de producción deben llegar por secretos server-side (`R2_ACCOUNT_ID`, `R2_BUCKET_NAME`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`). Nunca deben llegar al navegador, Firestore, logs o reportes.
- La limpieza elimina objetos temporales expirados y sus registros de sesión. Antes de tocar R2, un claim transaccional en el journal separado `memberImportCleanupJournal`, por `sessionId`, revalida `nextCleanupAt`, incrementa el intento y persiste de una vez el nuevo `nextCleanupAt` de backoff acotado, `status=running` y un lease de ejecución de 5 minutos (`leaseId`/`leaseUntil`). El journal conserva también `objectKeys` y `lastError` sanitizado.
- Después del claim se vuelve a leer y validar el journal antes del primer delete. Los fallos de R2 o de `sessions.remove` se escriben con backoff de 1, 2, 4 y 8 minutos, acotado a 15 minutos; el quinto intento queda en `failed` para intervención/alerta. Si falla `recordFailure` o cualquier persistencia posterior, el claim `running` ya conserva el intento, backoff y lease: la siguiente ejecución espera ambos gates, revalida el lease/contador y nunca supera cinco intentos. Las sesiones concurrentes quedan aisladas por lease y una sesión problemática no detiene a las demás.
- El trigger server-side `cleanupExpiredMemberImportSessionsSchedule` se ejecuta cada 15 minutos en UTC. Las operaciones R2 no usan reintentos infinitos: una sesión fallida se conserva para el siguiente backoff y nunca se procesa después de alcanzar el máximo.
- Si falla el store normal, el journal puede continuar el cleanup sin depender de actualizar la sesión. Si `listDue`, `claim`, `get` o la validación del journal falla, no se toca R2 y el handler propaga un error sanitizado fail-closed; las demás sesiones del lote continúan solo cuando el journal global sigue disponible. Si el journal queda completamente indisponible, la intervención manual obligatoria es abrir el circuit breaker del scheduler, restaurar/verificar el journal y reconciliar cada object key en R2 antes de reanudar. No existe reintento automático ilimitado ni una garantía automática durante una pérdida simultánea del journal y R2; si falla la escritura de un resultado posterior al claim, también debe intervenirse manualmente.
- La paginación de Members requiere el secreto server-side `MEMBER_PAGE_TOKEN_SECRET` (mínimo 32 caracteres); los tokens llevan firma HMAC y quedan ligados a academy y filtros.

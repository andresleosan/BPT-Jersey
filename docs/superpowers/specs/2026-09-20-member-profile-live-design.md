# Member profile live data — C1 / S3 design

Date: 2026-09-20. Status: proposed design; operator decisions listed below. **No implementation authorised by this document.**

Baseline inspected: `4ee9c96`, branch `feature/member-profile-live`, worktree `/root/BPT-Jersey-s3`. Source references below are relative to that worktree and use baseline line numbers. This is a source-code review, not a new production census, deployment verification or rendered-page audit.

## 1. Purpose and boundaries

Make Plan, Payments, Classes and Notes useful in the canonical office record at `/admin/members/profile?id=<studentId>`. Preserve its shell, tab navigation, Profile/Details, review flags, role restrictions and existing workflows. “Live” means a fresh canonical callable read on opening a tab or requesting Refresh, not a Firestore listener or continuous polling.

Authoritative context:

- `docs/adr/ADR-009-students-canonical-member-directory.md:23`: `students` is operational identity, administrative extension is `studentAdminProfiles`, membership/finance authority belongs to their aggregates; no implicit identity matching or permanent dual-write.

## 3. Target behaviour

### 3.1 Identity and migration states

Keep canonical profile URLs exclusively keyed by `studentId`. Never substitute legacy member IDs, archive IDs, names, email or date of birth. Three outcomes must remain distinct:

1. **Canonical student found:** render the existing header/review flags and tabs. An absent admin extension is not a missing identity. A missing family, guardian or DOB must not block reading empty tabs; preserve the existing review actions and all operational write/eligibility guards.
2. **Archive record unresolved:** retain the archive profile; add a clear canonical-record notice and an explicit “Open live record” action that uses the existing resolver. On null, show “Live record not linked yet. Review member migration or find an existing member before creating a record.” Offer “Review member migration” (`/admin/members/migration`) and a secondary existing member-search route. Do not promise the record is necessarily eligible for a queue decision: archive-only and skipped records exist. Keep the selected archive record and its data visible. No automatic migration, full queue fetch per record or retries pretending to repair it. After a decision, the operator can retry the explicit lookup.
3. **Canonical URL missing/not found:** neutral “Live member record unavailable. It may not have been created yet.” Offer Back to members and, for office only, Review member migration / Imported archive. Do not assert a migration status from a 404. Invalid ID syntax retains the invalid-link state; permission, freeze, rate-limit and network errors retain distinct safe notices and appropriate retry/sign-in/wait guidance.

At `/admin/members`, add a persistent small notice alongside existing navigation: “This directory shows live member records. Members awaiting migration remain in the imported archive.” Link to the existing queue and archive (`/admin/members/search`). No hard-coded census/count or claim of complete migration. This lets the majority still awaiting decisions navigate usefully even though no canonical profile can exist for them yet.

For an unresolved archive member, **all four canonical blocks are unavailable pending identity**, not empty, unpaid, inactive or zero attendance. The archive's four sections continue to show their explicitly imported content; existing embedded controls are left intact. The new S3 entry path directs identity work to S1. Replacing/removing archive registration controls is not silently included in S3; see Open decisions.

### 3.3 Loading, errors and presentation

- Mount/fetch only the active office tab after a full canonical profile succeeds. Notes uses that profile response; Plan and Payments do not block each other. Classes sections fail/retry independently. No all-tenant financial or schedule fetch followed by browser filtering.
- Use existing admin panels, table wrapper, typography, status text and controls. Four tabs stay in their current order; Documents and Communication retain their current behaviour. Wide records stack label/value rows on narrow screens; long descriptions and payment references wrap. No new dependency or redesign of the shell.
- Local skeleton + `aria-busy` during reads; a failed read is never an empty state. Keep the header/tablist navigable on tab errors. A retry replaces a stale error and cannot retain another student's data. Refresh keeps context but labels previous rows as refreshing/unavailable if the refresh fails; it must not silently present them as current.
- Re-entering a data tab fetches fresh data; an explicit Refresh supports office work in another page. Student/role changes immediately clear tab data and invalidate outstanding responses. Do not store notes, receipts or member data in localStorage, URLs, console logs or general caches.
- Preserve tab roles, roving focus, ArrowLeft/Right/Home/End, Back/Forward and the Details/Manage unsaved-work guard (`member-record.tsx:162`, `:262`). Tab results announce status without stealing focus. Keep visible keyboard focus and 44px targets.
- Dates/times use `en-GB` and `Europe/Jersey`; amounts use integer GBP minor units formatted as currency. Null/unknown is labelled, not filled with today's date. No measured performance improvement is claimed; lazy bounded reads are the intended cost control.
- Coach/headCoach keep their existing Profile-only projection. No new finance/notes requests from those roles, including forged `?tab=` links. Backend checks remain authoritative; do not rely on hidden tabs.

## 4. Callable contracts and reuse

All inputs are closed/validated. Academy and actor come from verified auth, never request payloads. Reuse App Check and active office-role guards; no direct browser Firestore access or new security-rule grants. Each resource read validates tenant, document identity and student ownership. Domain contains only types, schemas and pure selection/formatting rules; Firebase remains in functions adapters and web callable clients.

### 4.1 Profile, Notes and identity bridge — no new callable

- `getMemberProfile({ studentId }) -> MemberProfile`, unchanged full/coach union. Office Notes consumes only `details.details?.internalNotes`; this is already obtained through the audited restricted read. No standalone notes request, new collection, or migration provenance exposed.
- “Edit in Details” retains `updateMember(UpdateMemberDetailsInput) -> { studentId, ...existing response }` through `saveMemberDetails`; S3 sends no separate notes-only mutation. Existing 2,000-character/control-character validation, clearing semantics, audit and role guards remain in the Details workflow.
- `resolveMemberSubscriptionProfile({ recordId }) -> { studentId: string | null }`, reused on explicit archive action. Only a successful resolution creates a canonical link in the UI; it does not write a source link. Conflicting links are an error, null is normal. Existing resolver covers both S1 office links and account links, unlike the current archive header's membership-number-only action.
- `listMemberMigrationQueue` / `decideMemberMigration` stay in the existing migration page. S3 only links there; no automatic queue decisions or parallel identity model.

### 4.2 Plan — existing readers suffice

Use `listMemberSubscriptions({ studentId }) -> MemberSubscriptionContext` and `listManagedPlans(null) -> ManagedMembershipPlan[]` through existing clients. The former's closed result is:

```ts
{
  studentId: string;
  fullName: string;
  eligiblePlanIds: PlanId[];
  memberships: Array<{
    membershipId: string; studentId: string; planId: PlanId;
    status: "trial" | "active" | "paused" | "overdue" | "cancelled";
    startsAt: string; endsAt: string | null; updatedAt: string;
  }>;
}
```

Evidence: `packages/domain/src/memberships/subscription-admin-contracts.ts:7–43`; `apps/functions/src/memberships/subscription-admin-callables.ts:16`. `listManagedPlans` includes inactive plans, which must remain available for historical labels; map only `planId/displayName`, with a labelled unavailable-name fallback rather than dropping a membership. Do not filter history through `eligiblePlanIds`. A catalogue read failure must not discard valid memberships; show IDs as references with “Plan name unavailable”.

The existing subscription reader fails above 100 memberships using limit 101 (`subscription-admin-service.ts:74–92`). Retain that explicit ceiling in S3 and show an unavailable/too-much-history notice rather than a partial history presented as complete. No pagination abstraction for a currently empty, capped collection. Validate returned student ID in the web adapter. Do not use unfiltered `listMemberships(null)`: for office it is academy-scoped (`membership-callables.ts:397`).

Apply the same raw `legacy-import` exclusion to this reader and the Profile membership-summary adapter before selecting a current plan; the same live record cannot be historical in one tab and current in another. Retain invalid-record errors in the subscription reader. The existing Profile adapter silently skips malformed records and reads at most 100 without overflow detection (`member-profile-firestore.ts:54`); do not describe that summary as a complete history. S3 does not broaden that separate header-loading contract.

S3 is read/navigation by default: do not mount `MemberSubscriptionEditor`, which couples writes and billing reads. Existing `manageMemberSubscription`, `updateMemberSubscription`, `createMembership`, `transitionMembership` and cancellation workflows remain at their current entry points.

### 4.3 Payments — existing student-scoped billing reader, small safeguards

Reuse `listMemberSubscriptionBilling({ studentId }) -> SubscriptionBilling[]` and `getMemberSubscriptionBilling` from `apps/web/src/lib/subscription-admin-client.ts`. Reuse the presentational `SubscriptionBillingHistory`, making only needed display/empty-state adjustments; do not reuse the editor's combined load/write lifecycle.

Each result has `membershipId`, `complimentary`, `currentInvoiceId: string | null`, `reason: string | null`, and `invoices[]` with `invoiceId`, `status`, `totalMinor`, `dueAt`, `paidAt: string | null`, `description`, `payments[]`. Receipts have `paymentId`, `amountMinor`, `method: cash | bank_transfer | other`, `reference`, `occurredAt`. Exact schema: `packages/domain/src/memberships/subscription-admin-contracts.ts:159`.

This traverses **all invoices attached to the student's memberships**, not just the current invoice. It may include other charge kinds linked to those memberships. It excludes unallocated family charges and siblings' memberships. Do not title it a complete family account. `listFinancialAccount` / `listRecentPayments` accept no student filter; `getFamilyFinancialAccount({ familyId })` is deliberately broader (`finance-callables.ts:356–407`) and is not a substitute.

Before S3 consumption, add these narrowly scoped reader protections without changing its public result shape:

1. Confirm the tenant's canonical student exists; today zero matching memberships alone yields `[]`, even for an absent student. An existing student with no family returns an empty result normally. Do not let a stale profile masquerade as a valid empty account after identity removal.
2. Exclude raw documents explicitly marked `source: "legacy-import"` before operational invoice/payment parsing, current-invoice selection and display. Exclude imported memberships from this operational traversal too. No `where(source != legacy-import)` shortcut: existing live records have no source field and must continue to read. Missing source on an otherwise valid existing operational record remains live; S2 must always stamp imported records. Unknown source values fail closed rather than silently becoming live.
3. Keep strict relationship validation and all existing caps: at most 100 memberships, 100 invoices per membership, 1,000 receipts per invoice-ID batch; reader fails on limit+1. An administration pointer to an excluded historical invoice fails as inconsistent, not “paid”. Do not hide malformed operational records as empty.

Evidence for current traversal/caps and missing student check: `apps/functions/src/memberships/manual-subscription-service.ts:28–64`, `:362–446`. This is bounded but can still be expensive at the ceiling; do not poll it, invoke it for every directory row, or claim it is paginated. Large imported histories require an S2 history reader, not raising these operational caps.

### 4.4 Classes — one new bounded read callable

Existing `listStudentBookings({ studentId }) -> { bookings: BookingRecord[] }` and `listStudentAttendance({ studentId }) -> { attendance: AttendanceRecord[] }` are student-scoped, but both Firestore implementations read an unbounded collection subset and cast raw documents. Neither returns session titles/start times/centres (`schedule-service.ts:1413`, `:1507`). The Firestore attendance implementation also returns correction records, whereas the in-memory implementation excludes them (`:2653`). `listAttendanceHistory` requires a session ID and returns corrections for that one session (`schedule-callables.ts:1013`); it is not a member history reader. Reusing these plus an academy-wide `listSessions` fetch would make the new tab unbounded and easy to miscount.

Add **`listMemberClassRecords`**, office-only, within the schedule feature. This is the only new public callable in S3. It serves one of the two sections per request:

```ts
type Input = {
  studentId: string;
  kind: "bookings" | "attendance";
  cursor?: { at: string; recordId: string };
};
type SessionLabel = {
  sessionId: string;
  title: string;
  startAt: string;
  endAt: string;
  locationId: string; // render through the existing centre labels
};
type BookingRow = {
  recordId: string;
  session: SessionLabel | null;
  requestedAt: string;
  status: BookingStatus;
};
type AttendanceRow = {
  recordId: string;
  session: SessionLabel | null;
  occurredAt: string;
  state: AttendanceState;
  method: CheckInMethod;
};
type Result =
  | {
      studentId: string;
      kind: "bookings";
      rows: BookingRow[];
      nextCursor: NonNullable<Input["cursor"]> | null;
    }
  | {
      studentId: string;
      kind: "attendance";
      rows: AttendanceRow[];
      nextCursor: NonNullable<Input["cursor"]> | null;
    };
```

Use existing domain enums; all instants are validated UTC ISO strings. The result contains no staff IDs, proximity measurements, raw notes, correction reasons, family IDs or membership/payment data. `session: null` means referenced session details unavailable; render the row with “Class details unavailable” and its recorded event time/status, not as an empty history.

Read algorithm and limits:

1. Validate Auth/App Check/active owner or administrator, read the directory state and student with the page query in a read transaction, reuse `selectAdminDirectoryReader` to require the stable canonical reader, validate the student with `parseStudentProfile`, then select the fixed collection for `kind`. `selectAdminDirectoryReader` is the existing state selector in `apps/functions/src/members/member-directory-state.ts`; do not recreate its transition rules. Do not call the restricted `memberProfileRecord` for every page: that would load unrelated administrative fields and consume its separate restricted-read budget. No legacy lookup or family requirement. Invalid/missing student returns not-found; directory freeze/unavailability stays an error.
2. Page 25 records plus one lookahead. Bookings filter `studentId`, order `requestedAt desc, documentId desc`; attendance filters `studentId` and `correctionOf == null`, order `occurredAt desc, documentId desc`. This displays **event order**, labelled as booking activity/attendance, not an upcoming-session agenda. Use the current canonical attendance state after correction; do not append correction rows to visits.
3. Cursor is an ordinary pagination position, not authority. Validate shape, timestamp and ID. Re-read its document under this academy; require same student/kind, matching order timestamp and canonical attendance status before `startAfter`. Changed/deleted/incompatible cursor yields a safe “History changed; refresh” error. Every page repeats auth/student filters. No new cursor secret or signed identity protocol is needed for non-sensitive canonical row positions.
4. Skip explicitly imported rows from this live stream before projection; fail on unknown source. Advance from the last scanned row, including skipped rows, so an all-import page cannot loop. `nextCursor` means more source records may exist, not an exact remaining count. An empty page with a continuation renders Load more, not “No attendance recorded”. Existing rows without a source marker remain operational only after normal validation.
5. Fetch at most 25 distinct referenced sessions for the displayed page, validate tenant/ID and return only the label projection. No full schedule catalog scan. Add the two required query indexes in `firestore.indexes.json` during implementation and test the actual Firestore adapter with synthetic emulator records. Endpoints must not perform collection-wide fallbacks when an index is absent.

Each section has its own Load more, Refresh, skeleton and retry; opening Classes requests its two initial pages. This avoids a generic merged activity feed, shared polymorphic repository or pagination redesign of older consumers. Existing booking, check-in and correction callables stay untouched.

## 5. How S2 historical import fits later

S3 establishes the stable screen boundaries, identity keys and difference between **operational records** and **imported history**. S2 can fill the latter without replacing the shell or any live block:

| Block    | S2 integration seam                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Plan     | Keep current memberships authoritative. If S2 has an imported plan snapshot to display, put it in a labelled read-only “Imported plan history” subsection below live memberships. C1's S2 description does not promise membership creation; S3 does not require it. An old Regyfit valid-until/status never grants current eligibility.                                                                              |
| Payments | Add “Imported payment history” beneath operational invoices/receipts. S2's student-scoped canonical history projection supplies original recorded date/description/amount when verifiable and an explicit imported label. These rows never enter current-invoice selection, balances, revenue, payment status, overdue enforcement or payment actions. This is a history display, not an operational financial read. |
| Classes  | Add a separate “Imported class history” subsection, using S2's canonical student-linked projection. An imported row may have a class label/date but no canonical session or booking; do not require fake sessions, memberships or attendance credentials. Do not mix imported counts into live attendance totals or eligibility without a later explicit decision.                                                   |
| Notes    | Keep the current office note separately editable in Details. Add a read-only “Imported notes” subsection for S2's canonical student-linked notes. Never append automatically into the 2,000-character office note, overwrite office edits or treat migration time as original note authorship.                                                                                                                       |

Do **not** prebuild these empty subsections, synthetic collections, generic history registries, importer interfaces or historical DTOs in S3. The concrete S3 seam is each existing tab component with its live content, beneath which S2 can render its own feature-owned history component. A short archive-availability sentence is sufficient until history exists. S2 will own the necessary reader/schema addition for payments/classes/notes after its storage design is approved; existing readers cannot magically accept that data today.

S2 must provide stable tenant/student linkage, server-owned `source: "legacy-import"`, deterministic import identity/deduplication and explicit unknown dates/amounts/statuses. S3 must not assume all 249 archive records resolve, every queue decision is `link`, any source event has a usable date, a captured amount is verified cash received, a class has a canonical session, notes have authors/timestamps, or that the archive is complete. A failed/unperformed import is not zero lifetime activity.

Before any S2 historical write into operational collections, S2 must update the domain parsers **and every affected financial reader/writer/aggregate** to exclude history from operational calculations. S3's local billing guard is not a claim of a completed global C1 exclusion. Finance/dashboard currently lack this provenance contract. S2 must prove mixed live/imported fixtures do not change balances, revenue, membership eligibility or quota. UI labels alone do not satisfy that gate. S2 also owns repointing legacy class audit events; S3 does not fall back to them.

## 6. Risks, exclusions and Open decisions

### Risks and mitigations

- **Empty production mistaken for a defect or debt:** neutral migration notices and canonical empty states; no seed data or inferred financial state. Missing student, empty data and failed read are distinct.
- **Unresolved is mistaken for unmigrated:** use resolver outcome wording, never match by names, and offer existing search/queue without creating anything.
- **Historical financial contamination:** raw provenance exclusion on S3 operational reads, separate historical UI, mandatory S2-wide exclusion gate. Do not claim the current schemas support `legacy-import` already.
- **False attendance totals:** canonical correction filter and no totals computed from a partial page. Tests must exercise the Firestore implementation, not only its divergent in-memory counterpart.
- **Source/read limits:** Plan and Payments retain visible hard limits; Classes pages and session joins are bounded. No silent truncation or claim that one page is a lifetime history.
- **Identity disappears after S1 revert:** clear stale data on not-found; no automatic recreation. The S1 runbook explicitly warns its revert does not check all later references (`docs/operations/member-unification-s1-runbook.md:369`). Once live activity exists, S1's identity-only revert is not a general S3 rollback procedure.
- **Broader-data and role leakage:** no family-account substitute, no coach requests, no note/receipt caching or raw backend errors. Keep auth/Google linking and existing attendance controls unchanged.
- **Backend/web mismatch:** unavailable callable/index produces a retryable section error, not fabricated history. This design does not establish which functions are deployed; any future release requires its own authorised verification.

Out of scope: implementation in this change; S1 decisions/backfills; S2 import/deduplication/notes-history storage/class audit rewrites; S4 viewer removal/redirects; deleting legacy data; new financial writes/refunds/reconciliation; plan-editor redesign; booking/check-in/correction UI changes; family/guardian onboarding redesign; coach financial access; complete family accounting; background listeners/polling; auth and Google linking; production operations.
